## 언제 도착하는가 — 두 갈래다

보내는 것은 언제나 즉시다. 갈리는 것은 **받는 쪽이 언제 들여다보느냐**이고, 거기에 길이 둘 있다.

```
상대가 살아 있고 호스트에 들어갈 구멍이 있으면
    send 가 그 자리에서 두드린다 → 상대가 곧바로 턴을 돌고, 그 턴의 훅이 배달한다
    관측: claude UDS 0.8초, codex queue 1~8초

그렇지 않으면 (상대가 없거나, 게이트가 꺼져 있거나, 두드리기가 실패하면)
    지금까지와 같다 → 상대가 다음에 활동할 때 훅이 배달한다
```

**두드리기는 내용을 나르지 않는다.** poke 는 "메일 왔다" 한 줄이고, 배달은 언제나 훅이 한다.
렌더링·예산·읽음 기록이 한 곳에만 있다는 뜻이고, 두드리기가 실패해도 잃는 것은 지연뿐이다.

`pager send` 는 어느 길로 갔는지 말한다.

예약된 깨우기 알림은 훅이나 `msg_list`가 편지를 처리한 뒤에 도착할 수 있다.
`UserPromptSubmit`에서 독립된 pager 알림이고 수신함 조회가 성공했으며 기다리는 편지가
없다면 그 프롬프트를 차단해 빈 모델 턴을 막는다. 편지 기록은 보존한다. 일반 사용자 입력,
인용된 표시, 사용자 지시가 덧붙은 입력은 차단하지 않는다. 수신함 조회 실패도 차단하지 않는다.
일반 사용자 턴에서 조회한 편지를 다시 주입하는 기존 동작은 유지한다.

재설치 후 훅은 교체된 실행 파일을 쓰지만 기존 `pager mcp` 프로세스는 이전 코드로 계속 돈다.
MCP 서버를 재연결하거나 공유 app-server를 재시작해야 한다. 데스크톱 창을 닫고 다시 열어도
공유 서버가 남을 수 있으므로 MCP 프로세스가 실제로 교체됐는지 확인한다. 공유 서버를 재시작하면
연결된 다른 채팅의 작업도 중단될 수 있다.

```
poked <이름> (uds) — written to its inbox; its own hook is what delivers
note: <이름> was not poked — it will be delivered on its next activity
```

`woken` 은 **커널이 프레임을 받았다**는 뜻이지 상대가 돌았다는 뜻이 아니다. 이 경로에는 읽기
단계가 없다. 실제로 닿았는지는 수신 측 `delivered_at` 이 답한다.

### 이름 뒤에 아무도 없을 때

두드리기 결과보다 **먼저** 확인하는 것이 있다. 그 이름을 들고 있는 세션의 프로세스가 아직 도는가.

```
note: <이름>'s session is gone — the message waits, but nothing will read it
      until a session in that workspace claims the name; pager who lists who can answer now
```

별칭은 세션보다 오래 산다 — 그게 인계를 가능하게 하는 성질이다. 그래서 죽은 수신함도 이름이
멀쩡히 해석되고, 발신자는 누군가 있다고 믿는다. 이때 두드리기 결과만 내면
`was not poked — it will be delivered on its next activity` 가 나오는데, **다음 활동이 없다.**
큐에 대해서는 참이고 독자에 대해서는 거짓인 문장이라, 아무도 없는 바로 그 순간에 안심시킨다.

판정은 **pid + 프로세스 시작 토큰**으로 한다(`sessionref.Alive`). heartbeat 가 아니다 —
`pager inbox` 의 `HOST` 컬럼과 같은 이유다. 그리고 **호스트를 확인할 수 없을 때는 "없다"고 하지
않는다.** 붙을 때 호스트 탐지가 실패한 세션은 죽은 게 아니라 모르는 것이고, 근거 없이 부재를
주장하면 살아있는 알림을 숨기게 된다. 확실할 때만 이 줄이 나온다.

CLI 와 MCP `msg_send` 는 **같은 문장**을 낸다. 문장은 `deliver.Presence.Note` 한 곳에서 온다.

## 보장 — 조건부다

이름을 "at-least-once"라고 부르지 않는 이유가 있다. 아래 전제가 깨지면 **출력 시도는 0회**일 수 있다.

```
보장:  PAGER_INJECT_TTL 안에 수신 세션의 훅이 실행되고 stdout 기록이 성공했다면,
       확정 전에 프로세스가 죽어도 lease 만료 후 재시도된다.

전제:  수신 세션의 훅이 TTL 안에 최소 1회 실행된다   ← 두드리기가 닿으면 즉시 충족된다.
                                                     닿지 않으면 세션을 방치할 때 깨진다
       훅이 DB에 접근할 수 있다                      ← fail-open이라 조용히 실패한다
       호스트가 additionalContext를 채택한다         ← 훅 계약에 ack가 없어 확인 불가

미보장: 확정 후 호스트가 그 출력을 버리면 재배달되지 않는다.
중단:   TTL 경과 후 자동 재시도를 중단한다.
```

**두드리기는 이 보장을 바꾸지 않는다.** 첫 전제가 훨씬 자주 충족되게 만들 뿐이다.

**중복 실행은 재시도의 대가다.** 같은 지시를 두 번 볼 수 있다. 주입 텍스트의 메시지 id는
관찰을 돕는 표시일 뿐 durable dedup이 아니다.

## 훅 등록 — 어느 이벤트를 걸 것인가

등록 스니펫 자체는 [../README.ko.md](../README.ko.md#설치)에 있다. 여기 있는 것은 그 스니펫이
왜 그 모양인가다.

**이벤트명을 인자로 주지 않는 형태(`pager hook`)를 권한다.** 페이로드의 `hook_event_name`을
쓰므로 오타가 불가능하다. 명시하고 싶으면 `pager hook UserPromptSubmit`처럼 쓰면 되고,
**대소문자는 가리지 않는다** — 다른 도구들이 같은 이벤트를 소문자로 쓰는 설정 파일에 나란히
들어가는 일이 흔해서다.

내부 타임아웃은 5초로 고정돼 있다. 바깥 타임아웃은 그보다 여유 있게 준다 (Claude는 ms, Codex는 초).

| 이벤트 | 등급 | 빠지면 |
| --- | --- | --- |
| `UserPromptSubmit` | **필수** | 인과 리셋이 안 일어나 hop이 영구 누적된다. 세션 기록·배달도 여기 의존 |
| `SessionStart` | 권장 | 새 세션이 대기 메시지·고아 수신함 안내를 다음 프롬프트까지 못 본다 |
| `Stop` | 은퇴 | 존재 이유가 "턴 종료 직후 배달" 하나였는데 두드리기가 그걸 대신한다. 걸어둬도 동작하지만 새로 걸 이유는 없다 |

> **Codex에는 Stop을 걸지 않는 것을 권한다.** Codex Stop 훅이 `additionalContext`를 채택하는지는
> 미검증이다. 양쪽에서 검증된 필수 경로는 `UserPromptSubmit`이다.

## MCP 로스터의 `PURPOSE`

등록 명령은 [../README.ko.md](../README.ko.md#에이전트-안에서-쓰기-선택)에 있다. 도구 셋 중
`msg_roster`만 CLI에 없는 것을 낸다 — `pager who`와 같은 컬럼에 **`PURPOSE` 하나를 더** 붙인다.

```
NAME  TOOL    ROOT       HOST  LAST      PURPOSE
gupa  claude  ~/.config  live  just now  tmux 뱃지 다시 만들어줘
suzu  claude  ~/.config  live  4m ago    zsh 자동완성 추가
```

- **`PURPOSE`는 그 세션이 마지막으로 받은 사람의 지시**다. `UserPromptSubmit` 훅이 프롬프트를
  한 줄로 접어 80자까지 저장하고, 매 프롬프트마다 갱신된다. `ROOT`가 "어디에 있나"라면 이건
  "무엇을 하고 있나"이고, **같은 저장소에 세션이 둘 이상일 때 이것 말고는 구분할 방법이 없다.**
- **pager가 깨우려고 보낸 메시지는 `PURPOSE`가 되지 않는다.** 안 그러면 메일을 많이 받는 세션일수록
  "pager 메시지 확인"만 표시된다.
- 아직 아무도 프롬프트를 치지 않은 세션은 빈칸이다.
- **이 값은 이 기계의 모든 에이전트 세션이 읽을 수 있다.** `msg_roster`를 부르는 쪽이라면 다른
  프로젝트에서 친 지시문도 보게 된다는 뜻이다. 그리고 `sessions` 행을 지우는 코드가 없으므로
  (`prune`은 메시지만 건드린다) 죽은 세션의 값도 파일에는 계속 남는다. 로컬 DB의 신뢰 모델이
  `pager ls --session`과 같다는 전제 위에서 의도적으로 택한 것이다.
- `pager who`에는 나오지 않는다. 그 표는 이미 80칸 터미널에서 줄바꿈되고 있어서, 컬럼을 더하면
  사람이 읽는 쪽이 손해다.

## 명령 전체

README의 표는 자주 쓰는 것만 담았다. 전부는 이것이다.

```bash
pager who                                # 부를 수 있는 세션 목록 + 각 호스트 생존 여부
pager send hica "파서 작업 넘긴다"         # 보내기
pager ls                                 # 내 앞으로 온 것 (읽은 것까지 전부)
pager ls --waiting                       # 아무도 아직 안 챙긴 것만 — 작업 중 확인용
pager ls --expired                       # 자동 배달 창을 넘겼고 아직 아무도 안 챙긴 것
pager inbox                              # 대기 중인 메일이 있는 수신함 전부 (세션 무관)
pager whoami                             # 내 세션과 내 이름
pager alias review-box                   # 이름을 직접 고르기 (자동 이름을 대신한다)
pager claim review-box                   # 오프라인 수신함 이어받기
pager prune --dry-run                    # 보관 기한 지난 것 확인
pager export > backup.jsonl              # 저장소 전체를 JSONL로

pager send kipa@vm "…"                   # 다른 저장소의 세션 (저장소 사이의 relay 참고)
pager relay id                           # 이 저장소의 id — peer가 등록할 값
pager peer add vm --store <id>           # 다른 저장소를 이름으로 등록
pager peer ls                            # peer 목록과 각각 나갈 차례를 기다리는 메일 수
pager peer rm vm [--force]               # peer 지우기 (--force는 pending 메일을 취소한다)
pager peer rebind vm --store <id>        # peer를 다른 저장소 id로, 또는 다시 짝짓기
pager relay new-id [--force]             # 이 저장소에 새 id (백업에서 복원한 뒤)
pager relay out --peer vm                # transport 쪽: 나갈 차례인 레코드
pager relay in --peer laptop             # transport 쪽: 레코드를 수입하고 결과를 낸다
pager relay ack --peer vm                # transport 쪽: 결과를 반영한다
```

**"챙겼다"는 두 가지를 함께 뜻한다.** 훅이 메시지를 세션 컨텍스트에 주입했거나(STATE `delivered`),
에이전트가 MCP `msg_list`로 직접 들여다봤거나(STATE `seen`) — `--waiting`과 `--expired`는 둘 중
어느 것도 없는 것만 낸다. 그래서 `--waiting`은 "**내가** 못 본 것"이 아니라 "**아무도** 아직 손대지
않은 것"이다. `pager ls`는 무엇도 기록하지 않으므로(`ls --session`으로 남의 수신함을 들여다봐도
그쪽 메일이 소비되지 않는다) 사람이 보는 목록은 이 구별과 무관하다.

폴링으로 읽은 메시지도 **다음 턴에 훅이 다시 주입한다.** 중복이 아니라 의도다 — 그 사이 컨텍스트가
압축됐을 수 있어서, "누가 봤다"와 "지금 컨텍스트에 있다"는 같은 말이 아니다.

### `pager who` — 누구에게 보낼 수 있나

```
NAME  TOOL    ROOT                      HOST     LAST
gupa  claude  ~/Projects/portal/main    live     just now
suzu  codex   ~/.config                 gone     8m ago
hica  claude  ~/Projects/pager          unknown  21m ago
```

MCP `msg_roster`가 내는 것과 **같은 표다.** 렌더링이 한 곳에서 오므로 두 표면이 같은 질문에
다르게 답할 수 없다.

- **목록에 있다는 것과 살아있다는 것은 다르다.** 목록 기준은 `heartbeat_at`이고 기본 임계는
  12시간이라, 몇 분 전에 죽은 세션도 반나절 동안 남아 있다(실측: 8행 중 4행). 그래서 `HOST`가
  따로 있다 — 판정 근거와 세 단어의 뜻은 아래 `pager inbox` 항목과 같다.
- `LAST`는 마지막 훅이 언제 돌았나일 뿐이다. 긴 턴 중인 세션은 오래돼 보이고, 방금 죽은 세션은
  최근으로 보인다. **보낼지 말지는 `HOST`로 판단한다.**
- 죽은 세션도 숨기지 않는다. 이름 뒤에 아무도 없는 수신함은 `pager claim`으로 이어받는 대상이고,
  숨기면 그 후보가 안 보인다.

### `pager inbox` — 전역 대기 현황

`ls`가 "**내 앞으로** 뭐가 왔나"라면 `inbox`는 "**지금 누가** 메일을 기다리나"다. 세션을 해석하지
않고 저장소 전체를 본다. 대기가 0인 수신함은 빼고, 아무것도 없으면 `nothing waiting`을 낸다.

```
INBOX  WAITING  HOST
gupa   3        live
suzu   1        gone
hica   2        unknown
```

이 **세 컬럼이 외부 소비자가 파싱해도 되는 계약**이다 — tmux 상태바 배지처럼 전역 현황이 필요한
쪽이 SQLite 스키마를 직접 읽지 않아도 되게 하려고 존재한다. 컬럼을 적게 유지하는 것이 그 계약을
지키는 방법이다.

- `WAITING`은 `ls --waiting`이 그 수신함에 대해 세는 수와 **정의상 같다.** 같은 술어를 공유한다.
  자동 배달 창을 넘긴 것도 여전히 대기다(`expired ⊂ waiting`).
- `HOST`는 **pid와 프로세스 시작 토큰**으로 판정한다. `live`는 기록된 그 프로세스가 아직 돌고
  있다는 뜻이고, `gone`은 확실히 없다는 뜻, `unknown`은 물어볼 pid 자체가 없다는 뜻이다(붙을 때
  호스트 탐지가 실패했거나 별칭이 세션보다 오래 살아남은 경우). **`unknown`을 `gone`으로 취급하지
  마라** — 아무도 포기하지 않은 메일을 숨기게 된다.
- `HOST`는 **heartbeat가 아니다.** `heartbeat_at`은 훅이 돌 때만 오르고 훅은 턴 경계에서 도니까,
  긴 턴 중인 세션은 멀쩡히 일하면서도 stale로 보인다(실측 7분). "이 세션 소식을 최근에 들었나"는
  다른 질문이고, 그건 `who`의 `LAST` 컬럼이 답한다.
- 죽은 수신함을 **숨길지는 소비자가 정한다.** pager는 보고만 한다 — 알림은 버리고 싶겠지만
  감사(audit)는 바로 그것들을 보고 싶어 한다.

`pager attach`는 훅이 알아서 한다 — 훅을 등록하지 않고 손으로 쓸 때만 필요하다.

**플래그는 앞에 써도 되고 뒤에 써도 된다.** `pager send hica "본문" --human`과
`pager send --human hica "본문"`이 같다. 본문에 플래그 이름과 똑같은 낱말을 쓰려면 `--`로 끊는다 —
`pager send hica -- "--human 이라고 적고 싶을 때"`. `--` 뒤는 전부 본문이다. 선언되지 않은
`-`로 시작하는 낱말은 그냥 본문이므로 끊을 필요가 없다.

세션은 **별칭으로 주소를 받는다.** 별칭이 없으면 수신함이 없다.

### 이름은 자동으로 붙는다

훅이 한 번 돌면 세션은 `hica` 같은 **네 글자 이름**을 받는다. 자음과 모음이 번갈아 나오는
발음 가능한 문자열이고 **아무 뜻도 없다** — 뜻이 있어야 할 이유가 없고, 뜻을 만들려면 무엇에서
뜻을 가져올지 정해야 하는데 그 선택이 틀리면 조용히 엉뚱한 세션을 가리킨다.

이름이 없으면 발신자 표시가 세션 UUID가 되고, 받은 쪽은 누가 보냈는지 알 방법이 없다.
그래서 이름은 요청하지 않아도 붙는다. `pager who`로 남의 이름을, `pager whoami`로 내 이름을 본다.

2음절은 8100개다. 한 사람이 동시에 띄우는 세션 수에는 넉넉하지만 **이름은 회수되지 않으므로**
공간은 몇 년에 걸쳐 차오른다. 그래서 연속 8회 충돌하면 3음절(여섯 글자, 729,000개)로 넘어간다 —
조용히 포기하고 세션에 UUID를 남기지 않기 위해서다.

- **직접 고른 이름이 이긴다.** `pager alias review-box`를 하면 그때부터 그 세션은 `review-box`다.
  자동 이름도 계속 주소로 쓸 수 있다 — 세션이 이름을 여럿 갖는 것뿐이다.
- **호스트를 탐지하지 못하면 이름을 붙이지 않는다.** 별칭은 만들어질 때의 작업공간을 복사해
  고정하므로, 모르는 상태로 붙이면 그 이름은 영영 엉뚱한 작업공간에 묶인다. 이름이 없는 채로
  두고 다음 기회를 기다리는 쪽이 낫다.
- **자동으로 회수하지 않는다.** 한 번 준 이름은 그 세션 것이고, 시스템이 떼어 다른 세션에
  주지 않는다. 사람이 `pager claim`으로 가져가는 것은 그대로 된다.

수신 대상은
`별칭 완전일치 → 세션 ID → pm_ref 접미사 → 살아있는 것 중 유일한 부분일치 → 전체에서 유일한 부분일치`
순으로 해석한다.
**세션 ID와 pm_ref로 부를 때는** 그 세션이 이름을 여럿 가졌어도 모호하지 않다 — 잘못 갈 세션이
없으므로 대표 이름으로 접는다. 다만 서로 다른 세션이 걸리면(같은 pm_ref를 든 두 세션) 실패한다.
**부분일치가 여럿이면** 어느 이름을 말하는지 알 수 없으므로 후보를 보여주고 실패한다.

**축약은 살아있는 이름부터 본다.** 이름은 회수되지 않으므로 끝난 세션의 이름이 계속 쌓이는데,
그것까지 한꺼번에 상대하면 `pager who`로 보고 고른 이름을 축약해 부를 수 없게 된다. 살아있는
것 중에 유일하면 그것으로 확정하고, 하나도 없을 때만 전체로 넓힌다 — 그래서 **떠난 세션의
이름도 여전히 부를 수 있다.** 이어받으려고 남기는 메일이 갈 곳을 잃지 않는다.

### 별칭은 자동으로 넘어가지 않는다

같은 레포에서 어제 쓰던 별칭을 오늘 세션이 물려받으면 그건 오배달이다. 이어받기는
`pager claim`으로 **명시적으로** 한다. 이어받을 수 있는 수신함이 있으면 훅이 세션당 한 번 알려준다.

## 저장소 사이의 relay

머신마다 자기 저장소를 쓰고, 위의 모든 것은 그 안에서만 일어난다. 다른 머신의 세션에 닿으려면 두
저장소를 **peer**로 짝짓고, 직접 돌리는 무언가 — **transport** — 가 그 사이로 메일을 옮긴다.
pager는 네트워크 연결을 열지 않는다. 줄을 읽고 쓸 뿐이다.

### 주소

`name@peer`는 `peer`로 등록된 저장소의 세션을 가리킨다. `@`가 들어간 대상은 정해진 순서로만
해석된다. 정확히 그 철자인 로컬 alias가 있으면 그것(이 규칙 이전에 만들어진 이름), 아니면 등록된
peer의 `name@peer`, 그것도 아니면 `unknown peer`. 부분 문자열 단계로는 절대 넘어가지 않는다 —
`kipa@vm`이 로컬의 `kipa@vm2`에 조용히 맞는 것은 엉뚱한 머신으로 배달된 메일이기 때문이다. 새
alias에는 `@`를 쓸 수 없다. `@`가 없는 대상은 예전과 똑같이 해석된다.

원격 send도 다른 send와 똑같이 검사되고 기록된다(hop과 rate limit 포함). 다만 큐에 들어간다:
`sent #12 to kipa@vm (hop 0, human)` / `queued for peer vm; it leaves when the relay next runs`.
poke는 하지 않는다. 받는 쪽 저장소가 메시지를 수입할 때 자기 세션을 깨운다. 원격 본문은 64 KiB까지다.

### 두 저장소 짝짓기

```bash
laptop$ pager relay id                          # → a1b2…
vm$     pager relay id                          # → c3d4…
laptop$ pager peer add vm --store c3d4…
vm$     pager peer add laptop --store a1b2…
```

상대 저장소의 id를 명시적으로 등록하기 때문에, 엉뚱한 데이터베이스에 닿은 transport는 배달하는
대신 실패한다. peer 이름은 `a-z`, `0-9`, `-`로 된 1–32자이고 영문자나 숫자로 시작한다. 대문자는
pager가 이름을 받는 모든 곳에서 소문자로 바뀌므로 `VM`은 peer `vm`이다. 기존 alias가 `@이름`으로
끝나는 이름은 거부되므로, alias가 peer를 가리는 일은 생기지 않는다.

### transport 계약

명령 세 개를 파이프로 잇는다. 방향마다 한 바퀴:

```bash
# laptop → vm
pager relay out --peer vm | ssh vm pager relay in --peer laptop | pager relay ack --peer vm
# vm → laptop
ssh vm pager relay out --peer laptop | pager relay in --peer vm | ssh vm pager relay ack --peer laptop
```

ssh는 예시일 뿐이고, 줄을 옮길 수 있으면 무엇이든 된다. pager의 보장은 줄을 **잃거나, 반복하거나,
중간에 자르는** transport에서도 유지된다. 순서만 바꾸지 않으면 된다:

- `relay out`은 읽기만 한다. 최종 결과가 ack되기 전까지는 매번 같은 pending 레코드를 같은 순서로
  낸다(`--limit`, 1–1000, 기본 100).
- `relay in`은 레코드마다 따로 판정하고 commit하며, 레코드마다 결과 줄을 하나 낸다. 반복된 레코드는
  첫 사본에 답한 대로 답하고(`duplicate`, 또는 `rejected: previously rejected`), 빠진 레코드가 있으면
  그것이 올 때까지 멈춘다(`deferred`, `gap`). 빈 줄은 건너뛴다.
- `relay ack`은 batch 전체를 먼저 검증한 뒤에만 바꾸고, 최종 결과를 받은 메시지를 닫는다. 같은
  결과를 두 번 적용해도 바뀌는 것이 없다.

| 상태 | 최종 | 뜻 |
| --- | --- | --- |
| `imported` | 예 | 수신자의 수신함에 기록됨. 수신자를 poke한다 |
| `duplicate` | 예 | 이미 있다 — 재전송이거나 이미 수입된 것 |
| `rejected` | 예 | 배달할 수 없다(없는 alias, 범위 밖 hop 등). 보낸 쪽에 bounce가 간다 |
| `deferred` | 아니오 | 지금은 안 된다: 빈틈, 또는 peer별 상한(`retry_after_ms`가 언제인지 알려준다) — 그 자리에서 멈춘다 |
| `refused` | 아니오 | 스트림이 잘못됐다: 다른 저장소, 모르거나 어긋난 link, 지원하지 않는 버전, 깨진 줄 — 그 자리에서 멈춘다 |

| exit | 뜻 | transport가 할 일 |
| --- | --- | --- |
| 0 | 입력을 다 소비했거나 `deferred`에서 멈춤 | 계속한다. deferred 메일은 나중에 다시 |
| 1 | 데이터베이스나 I/O 실패 | 나중에 다시 |
| 2 | 프로토콜이나 구성 문제(`refused`, 등록되지 않은 `--peer`, 사용법) | 멈추고 사람에게 알린다 |
| 3 | 줄 중간에서 입력이 끝남(잘린 스트림) | 그 바퀴를 다시 돈다. 잘린 줄은 아무 효과가 없었다 |

이 코드는 `relay out`, `relay in`, `relay ack`의 것이다. 나머지 `peer`·`relay` 명령은 사용법을 틀렸을
때만 2로 끝나고, 아직 나갈 메일이 남은 `relay new-id` 같은 거부는 1로 끝난다.

transport는 또한:

- **hook이 쓰는 것과 같은 pager 바이너리**를 실행해야 한다 — ssh 아래에서는 `PATH`가 다른 바이너리를
  찾을 수 있다. 더 오래된 바이너리는 새 데이터베이스를 거부하고, 더 새 바이너리는 hook 밑에서 migration해
  버린다.
- 명령의 stdin에 쓰는 동안 stdout도 읽어야 한다. 그래야 파이프 버퍼(Windows에서는 작다) 때문에
  교착되지 않는다.
- `relay in`이 일찍 읽기를 멈춰서 `relay out`이 쓰기 오류로 끝나는 것을 실패로 세지 않는다.

### 레코드

한 줄에 JSON 객체 하나, LF로 끝난다. pager가 쓰는 것은 순수 ASCII다 — non-ASCII 문자는 전부
`\uXXXX` — 그래서 콘솔이나 파이프의 재인코딩이 망가뜨릴 수 없다. 읽을 때는 UTF-8과 CRLF 줄 끝을
받고, 맨 앞의 byte-order mark는 4개까지 건너뛴다(Windows PowerShell 5.1은 2개를 쓴다). 한 줄은
1 MiB까지이고, LF가 없는 줄은 완성되지 않은 것이라 아무 효과가 없다. 그 mark만 있는 스트림은 잘린
것이 아니라 빈 스트림이다.

```json
{"v":1,"kind":"msg","link":{"store":"<보내는 저장소>","id":"<link id>","seq":17},
 "origin":{"store":"<저장소>","id":4211},"dst_store":"<받는 저장소>",
 "to":"kipa","from":"sape","label":"sape","tool":"claude","hop":1,
 "sent_at":"2026-10-26T06:12:01.123Z","body":"…"}
{"v":1,"kind":"result","store":"<받는 저장소>","max_v":1,
 "link":{"store":"…","id":"…","seq":17},"origin_id":4211,"status":"imported"}
```

결과 줄에는 할 말이 있을 때 `reason`이, 기다릴 시간이 있는 `deferred`에는 `retry_after_ms`가 붙는다.

`link`는 빈틈 없는 일련번호 안에서 레코드의 자리를 정하고, `origin`은 메시지를 처음 쓴 저장소에서의
정체성이다. `from`은 보낸 사람의 답장용 이름이거나 `null`이고, `label`과 `tool`은 표시용이며, `sent_at`은
참고용일 뿐이다 — 받는 쪽은 자기 시계로 메시지 시각을 정한다. 원격 send에서 본문은 64 KiB, label은 1 KiB,
`@` 앞 이름은 128바이트까지이고, `relay out`은 받는 쪽이 버릴 만큼 긴 답장 이름(`from`)이나 호스트
이름(`tool`)을 싣지 않는다. 그래서 어떤 레코드도 줄 한도를 넘어 link를 막을 수 없다. `v`는 프로토콜
버전이다. 받는 쪽이 할 일을 바꾸는 필드는 추가만 해도 버전을 올린다(무시한 받는 쪽이 잘못 동작하므로).
순수한 설명용 필드는 버전을 올리지 않고 추가할 수 있고, 받는 쪽은 모르는 필드를 무시한다. 보내는 쪽은
레코드를 표현할 수 있는 가장 낮은 버전으로 쓰므로, 한쪽을 먼저 업그레이드해도 다른 쪽이 멈추지 않는다.

### 넘어가는 것, 막히는 것

- **인과 정보는 메시지와 함께 넘어간다.** hop은 추적 정보이며 3회 답장 예산이 아니다.
  확장 이벤트와 긴 사슬에는 v2 peer가 필요하다.
- **transport 제한은 데이터 구조에 적용한다.** 본문·프레임·발신 배치 크기 제한은 유지하고
  시간당 수입 총량은 제한하지 않는다. 원격 작업 신호가 unknown이면 루프라고 단정하지 않는다.
- **받는 사람은 어디서 왔는지 본다.** pager가 직접 쓰는 줄이라, 어떤 label도 그 줄을 만들거나 흉내낼
  수 없다:

  ```
  [#12] from sape
    relayed from peer laptop — reply to sape@laptop
  > the parser work is yours
  ```

  답장용 이름이 없으면 `no reply address; answer in your own output`이라고 쓴다.
- **거절은 bounce로 돌아온다.** 보낸 세션이 아직 가진 이름 앞으로 —
  `your message #12 to ghost@vm was not delivered: no such alias ghost; live names here: kipa`.
  세션 없이 보낸 메일이나 이름이 없는 세션의 메일에는 bounce가 없고, 결과는 메시지의 `relay_result`
  필드에 남아 export로 볼 수 있다. bounce도 로컬 메일처럼 alias를 따라간다.

### peer 수명 주기

- `pager peer ls`는 peer마다 `NAME`, 등록할 때 쓴 저장소 id인 `STORE`, 최종 결과를 아직 받지 못한
  그 peer 앞 메일 수인 `PENDING`, 지금 link에서 마지막으로 쓴 일련번호인 `SEQ`를 보여준다. `SEQ`는
  보낸 메일 수가 아니다. `peer add`, `peer rebind`, `relay new-id`는 저마다 새 link를 시작하고,
  rebind는 pending 메일에 그 link에서 1부터 번호를 매긴다.
- `pager peer rm vm`은 `vm` 앞 메일 중 최종 결과가 없는 것이 있으면 거부된다. `--force`는 그 메일을
  취소하고 보낸 사람마다 **그래도 도착할 수 있다**고 알린다 — transport가 이미 실어 갔을 수 있기
  때문이다. 취소된 메일은 다시 보내지 않는다.
- `pager peer rebind vm --store <id>`는 peer를 다시 짝짓는다(상대 저장소를 새로 만든 뒤 등). pending
  메일은 새 link로 옮겨 1부터 다시 번호를 매기고, 옛 link에 대한 결과가 늦게 와도 아무것도 바뀌지
  않는다. 옛 저장소로 이미 실어 간 것은 되돌릴 수 없으므로, 그 저장소가 살아 있으면 그쪽에도 갈 수 있다.
- `pager relay new-id`는 이 저장소에 새 id를 준다. **백업에서 복원한 저장소에 필요하다** — 복원은
  일련번호와 메시지 id를 되돌리면서 id는 그대로 두므로, peer가 진짜 새 메일을 이미 본 메일로 여긴다.
  pending 메일이 있으면 거부된다. 새 id로 다시 보낸 메시지는 이미 수입한 peer에게 새것처럼 보이기
  때문이다. `--force`는 그 메일을 먼저 취소하고 보낸 사람마다 알린다. 그다음 각 peer가
  `pager peer rebind <이름> --store <새 id>`를 해야 한다.

### 한계

- 받는 쪽이 이미 prune한 레코드가 다시 오면 — 수입 후 30일이 넘었고, 그 사이 결과가 유실된 채 어떤
  바퀴도 성공하지 못한 경우 — `rejected: previously rejected`로 답하므로, 실제로는 배달된 메시지에
  bounce가 갈 수 있다.
- relay는 한 단계뿐이다. 수입한 메일을 세 번째 저장소로 넘기지 않는다(`via`는 그 용도로 예약돼 있고,
  버전 1 수신자는 거부한다).
- 로스터는 다른 저장소의 세션을 보여주지 않는다. 그 이름은 그쪽에서 온 메일로 알게 된다. peer가
  등록돼 있으면 `pager who`와 `msg_roster` 끝에 peer 이름과, 이 저장소가 각 link의 동작을 마지막으로
  확인한 때가 한 줄로 붙는다(한 번도 없으면 `no relay seen`). 이 저장소에서 관찰한 것일 뿐, 상대
  저장소가 살아 있다는 뜻은 아니다.

| `PAGER_DB` | `~/.pager/msg.db` | 저장소 위치. 격리된 실험용 |
| `PAGER_SESSION` | — | 세션 해석 2순위. 훅이 심으면 자식 프로세스가 상속 |
| `PAGER_CLIENT` | 자동 탐지 | 호스트 툴 고정 (`claude`/`codex`). **인식 불가한 값이면 "호스트 없음"** |
| `PAGER_MAX_INJECT_BYTES` | `2000` | 주입 텍스트 전체의 UTF-8 바이트 |
| `PAGER_MAX_BATCH` | `5` | 한 번에 주입할 최대 건수 |
| `PAGER_MAX_BODY_RUNES` | `280` | 본문 절단 기준 (문자 단위) |
| `PAGER_INJECT_TTL` | `72h` | 자동 배달 창. 넘기면 재시도 중단 (삭제는 아님) |
| `PAGER_LEASE` | `2m` | claim 유지 시간 |
| `PAGER_ARCHIVE` | 켜짐 | `off`면 아카이브 없이 삭제한다. **`off` 외의 값은 전부 켜짐** |
| `PAGER_WAKE` | 켜짐 | `off`면 두드리지 않는다 — 배달은 훅에만 의존하는 예전 동작. **`off` 외의 값은 전부 켜짐** |
| `PAGER_LOOP_IDLE` | `2m` | 명시적 idle 왕복이 변하지 않을 때 알림을 멈추는 시간 |
| `PAGER_LOOP_SIGNAL_TTL` | `2m` | 상대 idle 신호 유효 시간. 오래되면 unknown으로 처리 |

`PAGER_WAKE` 를 켜두는 비용은 표면이 없을 때 디렉토리 한 번 읽는 것뿐이다.

**claude 를 두드리려면 받는 세션이 `CLAUDE_CODE_HARBOR_KITE=1` 로 떠 있어야 한다.** pager 는 이
값을 설정하지도 요구하지도 않고, 소켓이 등록됐는지만 관찰한다. 없으면 그냥 훅 경로로 떨어진다.
`~/.claude/settings.json` 의 `env` 에 넣으면 이후 새 세션 전부에 걸린다. 비공개 플래그이므로
릴리스에서 사라질 수 있고, 사라지면 두드리기만 조용히 멈춘다.

**Codex CLI가 PATH에 있고 네이티브 app-server 큐 메서드를 지원해야 한다.** thread에 저장된
rollout이 있어야 하므로 **턴을 한 번도 돌리지 않은 세션은 두드릴 수 없다.**
`CODEX_HOME`은 rollout 탐색과 큐 상태에 함께 적용된다.

Pager는 프로세스 간 SQLite 잠금으로 동시 전송을 직렬화해 thread마다 대기 알림을 최대 하나만
유지한다. 기존 중복 알림은 네이티브 큐 조회·삭제·추가 API로 합치며 Codex 큐 DB를 직접 수정하지
않는다. 편지는 모두 저장한다. MCP로 읽거나 훅으로 전달하면 불필요한 대기 알림을 지우고,
일반 사용자 입력은 보존한다. 훅 배치에서는 아직 읽지 않은 편지를 이미 조회한 편지보다 먼저
전달한다. 이미 처리된 알림은 모델 요청 전에 차단한다.

큐 API는 실험적이다. 미지원 응답, 잠금 실패, CLI 부재 시 알림을 무조건 추가하지 않고 편지를
보존해 둔다. Pager 업데이트 후에는 상주 MCP 클라이언트를 재시작해야 새 동작으로 검증할 수 있다.

기본값은 전부 **추정치**다. 실사용 지표 없이 정했다.

## 보관과 아카이브

보관은 30일이고 그 뒤 삭제된다. 훅 실행 중 하나가 24시간마다 한 번 수행하며, `pager prune`으로
직접 돌릴 수도 있다.

다른 저장소 앞 메일은 그 저장소가 최종 결과를 줘야 끝난 것으로 친다. 그 전까지는 아무리 오래돼도
남겨 둔다. 지우면 아무도 모르는 채 잃어버리기 때문이다.

**지우기 전에 반드시 파일로 남긴다.** prune은 지울 행을 `~/.pager/archive.jsonl`에 한 줄씩
append하고 `fsync`한 **뒤에야** 삭제한다. 파일에 쓰지 못하면 아무것도 지우지 않는다 — 디스크가 찬
상황이 영구적인 데이터 손실이 되는 것이 이 기능이 막으려는 바로 그 일이다. 대가는 **쓰기가 계속
실패하면 prune이 진행되지 않아 DB가 자란다**는 것이고, 그건 조용한 손실보다 낫다고 판단한 트레이드
오프다. 증상은 `pager prune`이 에러로 끝나는 것이고, 탈출구는 `PAGER_ARCHIVE=off`다.

아카이브 파일과 `pager export`는 **레코드 형식이 같다.** 그래서 필터는 `jq`가, 저장은 리다이렉트가
한다 — `pager export`에는 플래그가 없다.

```bash
pager export | jq 'select(.alias == "hica")'
cat ~/.pager/archive.jsonl <(pager export) | awk '!seen[$0]++'   # 전체 이력, 중복 제거
```

**중복은 계약이다 — at-least-once.** 같은 메시지가 두 번 이상 들어갈 수 있는 경로는 둘이다:
fsync와 삭제 사이에 프로세스가 죽는 경우, 그리고 그 사이 답장이 참조해 삭제에서 빠진 행이 다음
패스에 다시 기록되는 경우.

위 `awk`는 **줄 전체가 같을 때만** 접는다. 재시도로 생긴 중복은 같은 행을 다시 인코딩한 것이라
바이트가 같고, 서로 다른 메시지는 시각과 본문이 달라 둘 다 남는다. 다만 이건 **보장이 아니라
편의다** — DB를 지웠다 다시 만들면 id가 1부터 재시작하므로, 모든 필드가 완전히 일치하는 두 레코드가
이론상 하나로 접힐 수 있다. 아카이브 파일 자체는 언제나 모든 줄을 보존한다.

**두 prune은 서로 직렬화된다.** prune 게이트는 두 가지를 담고 있다 — 24시간에 한 번이라는 간격과,
동시에 둘이 돌지 않는다는 배제다. 수동 `pager prune`은 간격만 우회하고 배제는 지킨다. 이미 도는
prune이 있으면 아무 일도 하지 않고 그렇다고 말한다.

간격까지 함께 우회했을 때는 두 prune이 아카이브 파일의 **같은 오프셋을 계산해 서로를 덮어썼다**.
아카이브 추가는 트랜잭션 밖의 파일 쓰기이고 `O_APPEND`가 아니라 절대 오프셋에 쓰기 때문이다.
그때 결과는 깨진 줄이 아니라 **조용한 손실**이었다 — 파일은 완벽하게 파싱되고 레코드만 사라지며,
그 행들은 DB에서 지워진다. 수동 prune이 실패하면 리스를 즉시 놓으므로, 원인을 고친 뒤 곧바로
다시 실행할 수 있다.

**형식은 계약이다.** 각 줄은 `"v":1`을 달고 있다. 필드 추가는 그대로 두지만, 제거·개명·의미 변경은
`v`를 올린다. nullable은 생략이 아니라 `null`로 쓰고, 시각은 밀리초 3자리를 고정한 UTC RFC3339다.
배달 리스 부기(`claim_*`)는 담지 않는다.

한 가지 한계: 본문은 다른 에이전트가 쓴 텍스트이고 SQLite는 UTF-8을 검증하지 않는다. 유효하지 않은
바이트열은 인코딩 과정에서 U+FFFD로 치환되므로, **무손실은 유효한 UTF-8 본문에 한한다.**

## 협업 루프와 중요 이벤트

시간당 발송 총량이나 3홉 대화 제한은 기본적으로 없다. hop과 cause ID는 인과 추적용이다.
표현 범위 초과나 읽을 수 없는 인과 상태는 여전히 명시적 오류다. --human은 운영자 발신이라는
호출자의 선언이며 인증이나 일시정지 우회 기능이 아니다.

편지를 먼저 저장한 뒤 자동 깨우기를 결정한다. 일반 업데이트는 양쪽 로컬 세션이 명시적으로
activity=idle을 보고하고, 상대 신호가 최신이며, 같은 요청·응답과 진행 표식이
PAGER_LOOP_IDLE(기본 2분) 동안 변하지 않았을 때만 자동 깨우기를 멈춘다.
본문·진행 표식 변경, working/unknown 상태, 다른 task, 오래된 신호, 새 사용자 인과 epoch는
의심 상태를 초기화한다. 전체 메시지 개수로 차단하지 않는다.

신호는 선택적인 보고이며 의미 있는 진전을 검증하는 판정기가 아니다. activity를 생략하면
unknown이므로 정체라고 간주하지 않는다. 기존 래퍼는 그대로 사용할 수 있다. 실제 작업이
진행 중이면 working, 작업이 없다고 확인할 때만 idle을 사용한다. progress에는 실제 테스트 결과나
산출물 변경 표식을 담고 매 메시지마다 임의 토큰·시간을 만들어 넣지 않는다.
신호 없는 루프를 포함해 모든 무한 루프를 탐지하지는 못한다. 작업의 목표·종료 조건은 호출하는
워크플로가 관리한다.

kind=result, failure, release는 중요한 상태 이벤트다. 자동 깨우기 일시정지를 우회하며
다음 훅 배치에서 일반 업데이트보다 먼저 전달해 GPU 반납 통보가 밀리지 않게 한다.
단순 확인 답장은 update다. 같은 이벤트의 재시도에는 event_id(CLI는 --event)를 사용한다.
동일 내용이면 원래 ID를 반환하고 내용이 다른 ID 재사용은 거부한다. 아직 읽지 않은 이벤트의
재시도는 깨우기를 복구할 수 있고 읽었다고 기록된 이벤트는 다시 깨우지 않는다.
이벤트 ID나 중요도 선언은 인증이 아니다.

```sh
pager send vige "GPU released after application exit" --session "$SESSION_ID" \
  --task gpu-job --kind release --activity idle --event gpu-job-release
```

MCP msg_send도 선택적인 task, kind, activity, progress, event_id를 받는다.
일시정지 시 응답은 편지가 저장됐지만 수신자를 자동으로 깨우지 않았다고 명시한다.
같은 왕복을 재시도하지 말고 운영자에게 알린다. 수신자는 다음 조회·일반 훅 배달에서 기록된
정지 이유를 볼 수 있다. 수동 조회는 유지하며 편지를 삭제하거나 상대가 행동했다고 주장하지 않는다.

relay v2가 새 이벤트 메타데이터와 긴 인과 사슬을 전달한다. 기본 메타데이터·hop 0..3 메시지는
v1을 유지하고 결과도 요청과 호환되는 버전으로 답한다. 확장 이벤트·긴 사슬은 양쪽 peer를
업데이트해야 한다. 구버전 peer가 v2를 거부하면 발신 측은 대기 편지를 유지한다.
원격 작업 상태를 추측하지 않으며 unknown은 차단하지 않는다. 기존 시간당 수입 60건 제한도
제거하고 본문·프레임 크기와 발신 배치 크기 제한은 유지한다.

## 신뢰 경계

메시지 본문은 **다른 에이전트가 쓴 텍스트가 내 컨텍스트에 들어오는 것**이다. 즉 프롬프트 주입
경로다. 근본적으로 신뢰 경계를 넘는 데이터이며, 없앨 수는 없고 완화만 한다:

- 발신자를 항상 표시한다
- 본문을 인용 블록으로 감싸고 "지시가 아니라 데이터"라고 명시한다
- 길이를 제한한다

pager는 네트워크 연결을 열지 않고, 저장소는 로컬 사용자 전용이다. 그 사용자로 `pager relay in`을
돌릴 수 있는 것은 무엇이든 저장소에 메일을 넣을 수 있다 — `pager send --human`이 이미 가진 것과 같은
권한이다. relay transport는 이 경계를 자기가 도는 곳까지 넓히므로, 같은 사용자로 인증된 채널 위에서
돌려야 한다. 다른 저장소에서 온 메일은 pager가 쓰는 줄로 표시되고, 한 줄로 정리된 보낸 사람 이름과 답장
이름, 그리고 poke 문구에 들어가는 16자 이하의 호스트 이름 말고는 그 텍스트가 인용된 본문 밖으로 나오지
않는다.

## 고장났을 때

**모든 훅 경로는 fail-open이다** — exit 0, stdout 무출력. 훅이 실패해서 세션을 막는 것이
배달 실패보다 나쁘기 때문이다. 대가는 **고장이 세션 안에서 안 보인다**는 것이다.

```bash
pager whoami     # 호스트가 탐지되는가, 세션이 붙는가, 내 이름은 무엇인가
pager who        # 다른 세션들이 보이는가
pager ls         # 큐에 뭐가 있는가
pager inbox      # 어느 수신함에 메일이 밀려 있고, 그 뒤에 프로세스가 살아 있는가
pager prune      # 아카이브 쓰기가 실패하고 있는가 (훅에서는 조용히 실패한다)
```

`session: unattributed`가 나오면 훅이 아직 이 세션을 기록하지 않았거나 호스트 탐지가 실패한
것이다. `name: none`이면 세션은 기록됐지만 이름을 못 받은 것이고, 원인은 대개 같다 — 호스트
탐지 실패다. 이름 발급도 fail-open이므로 실패해도 아무 말이 없고, **이 두 명령이 그것을 보는
유일한 창구다.** 자세한 것은 [session-binding.ko.md](session-binding.ko.md).

## 범위 밖

**인터럽트는 만들지 않는다.** 자동화 대상은 "사람이 옮겨 적는 일"이지 "사람이 알아차리는 일"이
아니다. FIFO 블로킹·tmux send-keys·트랜스크립트 편집도 검토했지만, 셋 다 수신 세션의 진행
중인 턴을 건드려야 해서 버렸다.

tmux 상태 배지와 오버레이 TUI는 후속 단계다.

### 실제 호스트 루프 회귀 테스트

`python scripts/codex-loop-smoke.py --pager /path/to/pager --codex /path/to/codex`로 실행한다.
격리된 임시 홈에 실제 Codex 세션 두 개를 만들고 로컬 Responses 공급자로
셸·MCP 도구와 큐 실행을 검사한다. 클라우드 모델은 호출하지 않는다. 실제 파일을
수정하는 정상 작업, 진전 없는 반복의 깨우기 중단, 자원 반납 이벤트의 우선 전달과
재시도 중복 제거를 검사하며 임시 증거를 보존한다. 실험적 큐 API와 네임스페이스
MCP 호출이 필요하다(Codex 0.165.0-alpha.1.2에서 검증). Windows에서 실제 실행했으며
macOS/Linux 실행은 미검증이다.
